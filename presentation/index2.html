Evalu

Set the scene briefly — three years ago, evaluation domain.

Business case

What we deliver

"Two columns — the pain on the left, the AI-driven outcome on the right. The whole goal is shifting work the AI is genuinely good at — judgment over text — off humans."

Validate Feedback

Real-time feedback quality check

What it delivers

  • Real-time KPI coverage check
  • Targeted follow-up suggestions
  • Less rework, faster cycles

How it's built

  • 4-criteria LLM evaluation
  • Schema-bound JSON output
  • Single pass per evaluator

Tools OpenAI gpt-3.5-turbo LangChain ResponseSchema

The 4 criteria are clarity, specificity, informativeness, and KPI alignment — explicit in the system prompt. Without them the model evaluates with one fuzzy "is this good?" notion. Output schema: array of {question, is_sufficient, suggestions} — one entry per KPI question. Single LLM pass per evaluator/employee combination, results written back to the evaluation table. The win for the reviewer: they see why their feedback is insufficient — not just "bad" — and what to add.

Score Performance

Rubric-grounded competency scoring

What it delivers

  • 1–10 competency scores
  • Defensible & consistent
  • Actionable for managers

How it's built

  • 10-level rubric in prompt
  • temperature=0.0
  • Score 5 = "insufficient info"

Tools OpenAI gpt-3.5-turbo LangChain StructuredOutputParser

The full rubric goes in the system prompt — 1 Unsatisfactory through 10 Exceptional, with named gradations between. temperature=0.0 so the same feedback always gets the same score. The clever bit: score 5 is reserved as a neutral fallback when feedback is insufficient. The model has an honest answer instead of being forced to invent a score. That single design choice is what makes the scoring defensible — managers know a 5 means "we don't know yet," not "average." Schema: array of {question, score: int} — one entry per competency.

Generate Reports

Synthesized performance reports — not regurgitated

What it delivers

  • PDF report per employee
  • Reads like analysis, not copy-paste
  • Actionable recommendations

How it's built

  • Anti-regurgitation prompt
  • Safety guardrails in system prompt
  • Structured 4-field output → PDF

Tools OpenAI gpt-3.5-turbo LangChain SystemMessage PDF rendering

"Anti-regurgitation" is the unique technique — the prompt explicitly forbids quoting feedback verbatim. Without that constraint, the model just paraphrases. With it, you get real synthesis. Safety guardrails in the system prompt: no bias, toxicity, harmful content, no socially inappropriate language. Important for an HR-facing product. Output is 4 fields — employee_name, strengths, weaknesses, areas_for_improvement — synthesized as JSON, then rendered to PDF for delivery.

Script Outline Generator

Idea + duration → structured video outline

What it delivers

  • Author controls arc & total length
  • Optional book PDF as grounding
  • Sections w/ durations & prompts

How it's built

  • OpenAI Assistant + strict JSON
  • file_search reads attached PDF
  • Thread persists into next stage

Tools OpenAI Assistants API gpt-4o-mini file_search Strict JSON Schema

Output schema: {sections: [{title, duration, prompt, image_prompt}]}. Each section carries its own generation prompt for the next assistant — so the outline generator decides not just what each section covers but how the script writer should approach it. The thread reuse is the subtle bit — the OpenAI thread created here persists and is reused for section script generation. Context flows downstream automatically without re-prompting. Total runtime always lands in target window because the prompt explicitly enforces that the section durations sum to the requested length.

Section Scripts — with SSML

The AI inside that makes voiceover sound human

What it delivers

  • Prosody-aware narration
  • Sounds human, not robotic
  • Per-scene paired image prompts

How it's built

  • Specialized SSML prompt budget
  • Thread reused from outline
  • Per-section graceful failure

Tools OpenAI Assistants API gpt-4o-mini SSML markup Thread reuse

This is the wow moment. Slow down. Most AI narration sounds robotic because the AI generates plain text and the TTS engine reads it flatly. The trick is generating SSML — text plus prosody markup. The prompt is very specific about the budget: • <prosody> rate adjustments stay between +3% and +8% • <break> 200–400ms for natural breath, 500ms+ only for drama • <emphasis> "strong" reserved for 3–5 key moments per minute That's not a stock prompt — it's tuned from listening to a lot of bad AI narration. Schema: {scenes: [{scene_text, image_prompt}]}. Per-section error tracker means a bad section doesn't kill the pipeline.

YouTube Metadata + Thumbnail

How it's built

  • 2 dedicated assistants
  • TF-IDF + trending keywords
  • Prompt → Freepik for image

Tools OpenAI Assistants API TF-IDF Freepik (image gen) Strict JSON Schema

Two assistants here — clean separation. • Metadata generator: combines a brand title pattern with AI-generated supplement to hit exactly 100 characters. Description targets 250–300 words with mobile-optimized line breaks (<60 chars/line) and natural keyword integration. TF-IDF over the script + trending YouTube terms drives keyword choice. • Thumbnail prompt generator: takes the idea description + scenes, synthesizes a visual concept. Output prompt is fed to Freepik to generate the actual image. Decoupling AI prompt generation from image generation means we can swap image providers without touching the prompt logic.

Section 3 · open source · 2026

translate-local

Local-first AI translation CLI.

Open source. Built on my own time. The depth piece.

Business case

The problem

  • Cloud translation APIs leak sensitive content — legal, medical, internal docs
  • Off-the-shelf MT can't enforce a custom glossary — branded terms get lost
  • Sentence-level translation is context-blind — same word, different doc, different meaning

What we deliver

  • 100% local — TranslateGemma 12B via Ollama, zero data leaves the machine
  • Glossary enforcement with strict-mode retry on misses
  • Project-aware translation via TF-IDF retrieval over your files
  • Vision translation, streaming output, VRAM-aware
Three real problems. The third — context-blindness — is the one most users don't realize they have until they see the difference.

Glossary Enforcement

Brand and legal terms always translated correctly

What it delivers

  • Custom term dictionary
  • Strict or prefer mode
  • Coverage metric per call

How it's built

  • XML tag injection
  • Unicode-aware matching
  • Validate-and-retry on misses

Tools TranslateGemma 12B Ollama SQLite (glossary store) Unicode regex

Tag format: <term translation="X">source</term> — injected into the source text before the model call, stripped after. The matcher is Unicode-aware: regular \b for ASCII terms, \p{L} lookarounds for non-Latin scripts (Arabic, CJK). Most regex glossary matchers break on these — translate-localhandles them correctly. Longest-match greedy with an occupancy bitmap so no two terms overlap. Tag stripper handles three failure modes — complete, unclosed, and bare opening — defensive against the model not following instructions perfectly. Strict mode retries up to 2× on missing terms, then fails. Prefer mode allows partial matches. Coverage ratio returned on every call so callers can decide.

Context-Aware Translation

Same word, different document, different translation

What it delivers

  • Project docs as knowledge source
  • Picks up implicit terminology
  • .txt / .md / .mdx / .rst

How it's built

  • Local TF-IDF index in SQLite
  • Top 5 snippets per query
  • Two-pass indexer in one txn

Tools SQLite (bun:sqlite) TF-IDF Bun runtime

The pitch (say this first):
"Imagine you have a folder of your company's contracts. You translate a sentence. translate-local finds the few contract files most relevant to your sentence, hands them to the AI as reference, and asks for the translation. The AI matches your existing terminology automatically."

One-example walkthrough:

① Setup — one command: translate-local context add ~/legal-docs. Tool walks the folder, reads every file, figures out which words "characterize" each file — words that appear a lot in that file but rarely in the other files in the same folder. Saves those characteristic words in a small SQLite database.

② Translate — you translate "open a bank account." Behind the scenes, the tool breaks your sentence into words, asks the database "which files have these words as their characteristic words?" Sorts by best match, picks the top 5.

③ Inject — those 5 files get prepended to the prompt under "Context:". The AI uses them as reference and translates using the same terminology your contracts use.

Land the punchline:
"Pure SQL. No machine learning at retrieval time. Runs on any laptop."

If asked "what does TF-IDF mean?":
"TF-IDF stands for Term Frequency – Inverse Document Frequency. It's a classical information-retrieval algorithm — pure arithmetic, no machine learning. Invented in the 1970s, still a workhorse of search engines today.

Two ideas multiplied:
• TF = how often a word appears in this file
• IDF = how rare the word is across the other files
A word scores high when it appears often here but rarely elsewhere — the words that make a file distinctive. 'Arbitrate' in a contract scores high. 'The' appears everywhere, scores zero — useless. The high-scoring words are the ones that tell you what a file is really about."

If asked "is it AI?":
"No — TF-IDF is just arithmetic. The AI in translate-local is the translation model itself. TF-IDF is the retrieval algorithm that decides which reference docs to feed the AI."

If asked "why not embeddings?":
"Embeddings would let you match 'arbitrate' with 'litigate' semantically. TF-IDF won't — it's exact-word match. But for domain terminology, exact match is usually what you want: if your contracts say 'arbitrate', you want the AI to translate that word the same way every time. And TF-IDF needs zero GPU, zero model downloads. Right tool for the job."

If asked deep technical details:
• Tokenize = lowercase + regex /[a-z0-9]{3,}/ — no stopwords, no stemming
• Index stores top 100 TF-IDF terms per file
• Snippet = first 500 chars of each matched file (bounded prompt size)
• Atomic two-pass indexer in one SQLite transaction
• Re-index with translate-local context index after editing files

Vision Translation

Translate text inside images

What it delivers

  • translate-local --image screenshot.png
  • Screenshots, scans, UI, diagrams
  • PNG / JPEG / WebP / GIF / BMP

How it's built

  • Base64 → Ollama images field
  • Same model, vision mode
  • Pre-flight validation

Tools TranslateGemma vision mode Base64 encoding Pre-flight validation

The pitch (say this first):
"Point translate-local at any image — a screenshot, a scanned document, a foreign UI — and it gives you back the translated text. One command. The trick is we use a multimodal model, so reading the image and translating happen in a single pass."

One-example walkthrough — translate-local --image screenshot.png --to ar:

① Validate — CLI checks the file is a supported type (.png .jpg .jpeg .webp .gif .bmp), exists, is under 10 MB. Typed errors so the user gets a clear message — not a generic crash later.

② Encode → base64 — image bytes are base64-encoded into a string. That's all. No image library, no OCR step on our side.

③ Hand to Ollama — we POST to Ollama's /api/generate with images: [base64_string] in the body. Ollama's API accepts that natively for multimodal models.

④ Model does both — TranslateGemma 12B is multimodal. It reads the pixels, extracts the text, and translates in one forward pass. No separate OCR step in our pipeline.

Land the punchline:
"No separate OCR. The model sees the image and translates the text in one go — same model we use for everything else."

If asked deeper details:
• Glossary tag injection skipped (can't put XML tags inside pixels), but glossary terms still pass through as plain instructions in the prompt
• Same NDJSON streaming and postprocessing as text translation downstream — vision is invisible to the rest of the pipeline
• Pluggable adapter — swap to another multimodal model (Qwen-VL, LLaVA) by implementing one interface
• Typed errors: IMAGE_INVALID_TYPE, IMAGE_TOO_LARGE, IMAGE_NOT_FOUND, IMAGE_READ_FAILED
