Section 1 · 2023

Evalu

AI-powered 360° employee evaluation.

"First project — Evalu. Three years ago. The premise: take 360° performance reviews, which are slow and inconsistent, and use AI to make them fast and reliable." Quick context. Move to the problem slide.

The problem

  • 360° performance reviews take weeks per cycle
  • Feedback quality varies wildly across evaluators
  • Manual scoring is biased and inconsistent
  • Synthesizing 10+ pieces of feedback into a report is laborious
Frame the pain. "If you've ever been through a 360° review cycle, you know it's painful — for HR, for managers, and for the employees waiting on it. Some reviewers write paragraphs, others write 'good job'. Then someone has to score everyone consistently and turn it all into a coherent report." The point: this is a great use case for AI because the work is mostly *judgment over text* — exactly what LLMs are good at.

AI features I shipped

FeatureWhat it does
Validate Feedback LLM evaluates feedback on 4 criteria (clarity, specificity, informativeness, KPI alignment). Returns is_sufficient + targeted follow-up suggestions per KPI question.
Score Performance Auto-scores each competency on a 10-level rubric (1 Unsatisfactory → 10 Exceptional). Score 5 reserved as a neutral fallback when feedback is insufficient — model has an honest out instead of hallucinating.
Generate Reports Synthesizes feedback into structured reports: strengths, weaknesses, areas_for_improvement. Prompt explicitly forbids reusing feedback verbatim — forces real synthesis.
Categorize Feedback Auto-tags free-text feedback against arbitrary category sets. Two implementations: OpenAI + local FLAN-T5.
Walk through the four features briefly. Don't read the table — use it as an anchor. • Validate Feedback: "We don't just ask 'is this good?' — we check four specific criteria. The AI tells the user *why* feedback is insufficient and asks targeted follow-ups." • Score Performance: "Ten-level rubric. The clever bit is that 5 is reserved for 'insufficient information' — so the model has an honest out instead of inventing a score." • Generate Reports: "The prompt explicitly tells the model NOT to copy feedback verbatim. That forces real synthesis." • Categorize Feedback: "Two backends — cloud OpenAI for quality, local T5 for cost and privacy. Customer choice." End with: "All four return structured JSON, validated. Nothing free-text downstream."

Stack & techniques

Stack

  • OpenAI gpt-3.5-turbo via LangChain ChatOpenAI
  • LangChain StructuredOutputParser + ResponseSchema
  • FLAN-T5 — local fallback for categorization
  • FastAPI backend, React frontend

Techniques

  • Schema-bound outputs — every call validated, never raw text
  • Rubric-grounded scoring — full 10-level rubric, temperature=0.0
  • Safe-fallback scoring — 5 reserved for "insufficient info" so the model can't hallucinate certainty
  • Anti-regurgitation prompt — report prompt forbids quoting feedback wording, forces synthesis
  • Multi-criteria evaluation — 4 axes, not one vague "is this good?"
  • Safety guardrails — explicit ethical clauses in system prompt
  • Dual-model strategy — cloud + local for cost / privacy
The two ideas to land on this slide: 1. "Even in 2023, before strict-mode JSON existed in the OpenAI API, I was using LangChain ResponseSchema to enforce a JSON contract on every single call. Schema-first AI was the default, not the exception." 2. "The 'safe fallback' and 'anti-regurgitation' patterns are the kind of prompt design that comes from actually running these systems against real feedback and seeing where they fail. They're defensive prompt engineering." Don't read every bullet — call out 2-3 highlights and move on.

Section 2 · 2024

FlowVoke

Idea → video. Multi-step AI orchestration.

"Fast forward a year. Second project, much more ambitious scope. Take a book — like a PDF — and turn it into a finished YouTube video. Script, voiceover, images, thumbnail, SEO metadata, the whole thing, automated." Set the stakes: this is where the AI gets multi-step.

The problem

  • One educational video from a book = writer + narrator + editor + designer, days of work
  • Voiceover, visuals, SEO each need a different specialist
  • The bottleneck isn't any single step — it's the orchestration
"Producing one educational video the traditional way takes a team. And the interesting thing isn't that any one of those tasks is impossibly hard for AI — it's that *gluing them together reliably* is. That's the real challenge." This sets up the architecture story — the hard part isn't any model, it's the pipeline.

How it evolved

v1 — Initial approach

Book-driven

PDF → chapter structure → chapter summaries.

The chapter summary was the script.

Worked, but scripts read like summaries. No control over duration or pacing.

v2 — The pivot

Idea-driven, with optional book reference

Idea (+ optional PDF) → outline → section scripts (SSML scenes) → images + voiceover → metadata + thumbnail → render → upload.

Cleaner separation, controllable length, prosody-aware narration.

This is the iteration story — be authentic about it. "Originally, I built this book-first. Upload a PDF, summarize the chapters, treat the summaries as the script. It worked, but the output felt like book summaries — not videos. And I had no real control over how long the video would be." "So I pivoted. I separated the *idea* from the *source material*. The idea drives the outline; the source PDF becomes optional context. And I introduced a proper script generation step with SSML markup so the narration would sound natural, not robotic." The point for the client: "I shipped v1. I noticed the limits. I redesigned. That's how I work on AI projects — the first design is rarely the final one."

Stack & techniques

Stack

  • OpenAI Assistants API (gpt-4o-mini) with file_search for PDF grounding
  • Google Cloud TTS
  • Freepik image generation
  • Rails + Sidekiq — ~9 jobs end-to-end

Techniques

  • Strict-mode JSON schemas — OpenAI validates output shape, no parser failures
  • Detailed SSML prompt engineering — relative prosody, pitch budget +3–8%, breaks 200–400ms (natural) / 500ms+ (dramatic), 3–5 strong emphases per minute
  • Thread reuse — outline thread persists into section scripts, context carries
  • Resource lifecycle — every job tracks {assistants, threads, files} and cleans up explicitly
  • Exponential backoff retries with polled wait_for_run (300s timeout, 2s interval)
The hero point on this slide is SSML prompt engineering. Slow down here. "AI-generated voiceover usually sounds robotic because the AI generates *text*, and the TTS engine reads it flatly. To get human-sounding narration, the script itself has to carry prosody information — speed up here, pause here, emphasize this word." "So the prompt for the section script generator is very specific: use relative speed adjustments, not precise percentages. Pitch budget +3 to +8 percent. Breaks of 200 to 400 milliseconds for natural breath, 500-plus for dramatic effect. Three to five 'strong' emphases per minute, no more — otherwise it sounds melodramatic." "That's not a stock prompt. That's prompt design from listening to a lot of bad AI narration." Then: "Resource lifecycle — every job tracks the assistants, threads, and files it creates and cleans them up explicitly. No orphaned OpenAI resources, costs stay bounded."

Section 3 · open source · 2026

translate-local

Local-first AI translation CLI.

"Third project — and this one's different. translate-localis open source. I built it on my own time. The first two projects showed I can ship fast under pressure. This one shows what depth looks like when there's no deadline." Set the tone shift — same skills, different setting.

The problem

  • Cloud translation APIs leak sensitive content — legal, medical, internal docs
  • Off-the-shelf MT can't enforce a custom glossary — branded terms get lost
  • Sentence-level translation is context-blind: same word, different doc, different meaning
"Three real problems with how translation is done today. If you're a law firm, you can't paste a contract into Google Translate — full stop. If you have branded terminology, off-the-shelf MT will silently inconsistent it. And every existing tool translates one sentence at a time, blind to the rest of the document." "translate-localsolves all three locally."

AI features I shipped

  • Fully local — TranslateGemma 12B via Ollama, zero data leaves the machine
  • Glossary enforcement — XML tag injection (<term translation="X">source</term>) constrains the model; strict mode retries on violation
  • Context-aware — TF-IDF retrieval over project files; top snippets injected into the prompt
  • Vision translation — translate text inside images (PNG, JPEG, WebP, …)
  • Streaming output — token-by-token in CLI & TUI
  • VRAM-aware — auto-unloads model after each invocation
Walk through the features. Highlight the technically interesting ones: • "Glossary enforcement uses XML tag injection. Before the text goes to the model, I wrap glossary terms in custom XML tags that tell the model what the translation should be. After translation, I strip the tags. If a term is still missing, strict mode retries." • "Context-aware translation indexes the whole project locally with TF-IDF. When you translate a sentence, the most relevant snippets from the rest of your project get injected into the prompt. Same sentence translated in a legal document vs. a marketing brief produces appropriately different output." • "Vision translation — point it at an image, get translated text back. Uses the same model in vision mode." • "VRAM-aware — the 12B model is big. translate-localunloads it after each invocation so it doesn't hog GPU memory when you're not actively translating." Open source tone here — invite the client to look at the code if they want.

Stack & techniques

Stack

  • TranslateGemma 12B / Ollama
  • Bun + TypeScript (strict)
  • SQLite for glossary & context indexes
  • Commander (CLI) + OpenTUI (TUI)

Techniques

  • Tag-injection prompting — Unicode-aware word boundaries (\p{L}), longest-match greedy resolution
  • Validate-and-retry — strict glossary mode retries up to 2× on missing terms
  • NDJSON streaming with 10 MB safety ceiling against malformed responses
  • Pluggable adapters — clean interface for swapping models

Land the depth point. "The whole thing is a Bun monorepo with strict TypeScript. Glossary and context indexes are SQLite. Pluggable adapter interface — adding a new model means implementing two methods." "The XML tag stripping is more careful than it looks — it handles three cases: complete tags where the model used them right, unclosed tags where the model forgot to close, and bare opening tags. Defensive parsing because models don't always follow instructions." "All open source — the link's at the bottom of the slide. Audit it, run it, fork it."
